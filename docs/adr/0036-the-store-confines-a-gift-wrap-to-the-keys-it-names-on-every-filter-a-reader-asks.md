# 36. The store confines a gift wrap to the keys it names, on every filter a reader asks for

## Status

Accepted

Supersedes ADR-0035. Carried forward unchanged: a kind 1059 or 21059 event is served only to a connection authenticated as a key its `p` tag names, whatever the policy grants; a filter asking for gift wraps beyond the connection's keys is a read beyond scope, and one left able to match nothing is refused `CLOSED` `auth-required:`; a filter naming no kind is not a read beyond scope; no wrap's recipient is judged by parsing stored bytes. Revised: the store applies the rule on every filter, from its tag index, where the relay used to rewrite each filter, split it into a group sharing one limit and read each group on its own. A filter naming no kind, an `ids` lookup and a `#p` filter now return the reader's own wraps, every filter's limit is exact, and a `COUNT` is one store count. This record holds the complete current decision.

## Context

NIP-59 says "To protect recipient metadata, relays SHOULD only serve `kind 1059` events intended for the marked recipient", and NIP-17 says "Relays SHOULD protect message metadata by only serving `kind:1059` events to users p-tagged on the event (enforced using NIP-42 AUTH)". An ephemeral gift wrap, kind 21059, "has the same structure as `kind:1059`". Who a wrap is for is the one thing its outside reveals, and serving every wrap to anyone who asks hands over a map of who receives private messages, and when. A SHOULD that every host has to remember to implement is one most hosts miss, so the library applies it after whatever policy the host gives it.

ADR-0035 enforced the rule by rewriting the request. A filter naming a gift-wrap kind was split, and its gift-wrap half confined to `#p` holding the reader's keys; the halves stayed one group that shared the filter's `limit`, and the relay read each group with a store call of its own. A filter naming no kind could not be rewritten, because a NIP-01 filter cannot name "every kind but these", so the relay dropped every gift wrap such a filter returned, by the kind in the event's header. A `COUNT` was built from up to three store counts: all the filters, less the gift wraps any of them matched, plus those a filter naming their kind matched.

That had costs. A `REQ` with N filters cost N store calls. A filter naming no kind lost the wraps it matched after the store had already applied its limit, so its page came back short. `{"ids":[ownWrap]}` or `{"#p":[me]}` never returned the reader's own wrap, which a client authenticated as its recipient is entitled to. A count was arithmetic over counts that could each be approximate.

The relay already trusted the store to honour the `#p` it injected. The store holds a tag index, and "a gift-wrap kind only where a `p` tag names one of these keys" is one more condition on that index, which a store can apply on every filter before that filter's `limit`. Handing the store the reader's keys asks it for nothing it was not already trusted with, and needs no parse.

## Decision

- **Every read is a reader's.** `RelayEventStoreInterface::findByFilters(FilterCollection $filters, ActingKeys $reader)` and `::countByFilters(FilterCollection $filters, ActingKeys $reader)` take the reader's acting keys: the keys the connection has authenticated as, none for a guest and several for a connection that authenticated as several (NIP-42: "Relays MUST treat all pubkeys as authenticated accordingly"). On every filter, before that filter's `limit`, a store matches an event of a gift-wrap kind only where one of its `p` tags names one of those keys, and matches every other event as the filter alone decides.
- **`ActingKeys` is the one definition of the rule.** It holds the keys a request acts as: for a read, the keys the connection authenticated as; for a deletion, the deletion's signer (ADR-0038). `getConfinedKinds()` names kinds 1059 and 21059, `getKeys()` the keys, and `canRead(Event)` answers for an event a caller holds. A store that holds events asks `canRead`; a store with an index builds the same condition from the kinds and the keys. `ActingKeys` has no form meaning "every key", and the port has no read without one, so no read is unconfined. The only relay-internal read the library made, the deletion lookup, is now part of the store's delete (ADR-0038).
- **A `REQ` is one store read.** `StoredEventReadGate` asks the store once, for every granted filter and the reader's acting keys, puts what comes back in NIP-01's order (ADR-0039), and withholds what has expired (ADR-0014) or what the policy refuses (ADR-0022). **A `COUNT` is one store count**, for the same filters and keys, framed unchanged (ADR-0013).
- **The admitted read carries the reader's acting keys.** `ReadScopeGate` asks the policy, then builds an `AdmittedRead` from the policy's `ScopedFilters` and an `ActingKeys` of the connection's authenticated keys. The policy never sees or sets them, so no policy widens them, a tenant's included.
- **Live delivery applies the same rule.** `DeliveryGate::allowsLive` matches the subscription's filters, then asks the subscription's `ActingKeys::canRead` of the event it holds, then the policy. The registry keeps the acting keys each subscription was admitted under (`SubscriptionRegistryInterface::addSubscription($clientId, $subscription, $reader)`, `SubscriptionMatch::getReader()`), so a subscription's live events are confined as its stored ones were, and authenticating later widens nothing already open (ADR-0033).
- **When a read is beyond scope stays as it was.** `AdmittedRead::isBeyondScope()` is true when the policy narrowed the read, or when a filter names a gift-wrap kind without confining it, through `#p`, to keys the reader holds (`ActingKeys::narrows`); its stored events end with an `AUTH` challenge and an `EOSE` carrying `"auth"` (ADR-0004). `isWhollyBeyondScope()` is true when, besides, no filter can match anything the reader may read (`ActingKeys::leavesMatchable`); such a `REQ` is refused `CLOSED` `auth-required:`. A filter naming no kind does not narrow: it asks for no gift wrap by kind, and treating it as beyond scope would challenge almost every guest read.
- **The relay owns the rule; the store applies it.** Every store implementation runs the contract cases the library ships (ADR-0037).

## Consequences

- One store read per `REQ` and one store count per `COUNT`, however many filters the request holds.
- Every filter's `limit` is exact: a store confines before it limits, so a page is never cut short by a wrap withheld after the limit was spent.
- A reader receives its own wraps from any filter that matches them: one naming no kind, an `ids` lookup, a `#p` filter naming it.
- A `COUNT` is exact in one store query, and approximate only when the store says so.
- The `p` tag is matched by the store's tag index on the stored path and against the event the live path already holds; nothing parses stored bytes.
- A store that ignores the reader's acting keys serves every wrap to anyone. The contract cases are how a host shows its store does not. This is a breaking change for every host store: `findByFilters` and `countByFilters` take the reader's acting keys. `SubscriptionRegistryInterface::addSubscription` takes them too.
- `GiftWrapFilterRules`, `FilterGroupCollection`, `ScopedFilters::grouped()` and `::getGroups()`, `ReadableEventCounter`, and the withholding of every wrap a filter naming no kind returned, are gone.
- A filter naming a gift-wrap kind with a `#p` holding the reader and another key is still beyond scope, because it asks for the other key's wraps, and is answered with the reader's.
- A store matches a filter's `#p` and the acting keys as two conditions on the `p` tags. So a wrap tagging both another key and the reader is returned to the reader through a filter naming no kind, or mixing kinds, whose `#p` names only that other key, where ADR-0035's intersected `#p` withheld it. NIP-17 asks for "only serving `kind:1059` events to users p-tagged on the event", and the reader is p-tagged on that wrap, so serving it is what NIP-17 allows. A filter naming only gift-wrap kinds with such a `#p` is still refused `auth-required:`, because everything it asks for is another key's. In every case a wrap reaches a reader only when one of its `p` tags names one of the reader's keys; `GiftWrapConfinementTest` pins it across filters naming no kind, `ids`, `#p` and `authors`, stored reads, counts and live delivery of both gift-wrap kinds.
- Do not add a read without acting keys, a nullable `ActingKeys`, or a flag that lifts the confinement. Do not move confinement back into filter rewriting, do not judge a wrap's recipient at delivery by parsing stored bytes, and do not exempt a trusted client.
- Shared decision: nostr-adrs ADR-0122.
